# Orca survey 05: the terminal and the workspace UX

Read from `/srv/stacks/orca-refs/orca` at `1c2cf120e3` (2026-09-25). Paths are relative to that
repo root unless they start with `crates/` (Marley, `/srv/stacks/marley_ide`). Line counts are
non-test TypeScript (tests, harnesses and fixtures excluded) unless marked otherwise. Report 01
covers agent status, notifications and unread in depth; this report cites it rather than repeat it.

## 1. Summary

Orca's terminal is xterm.js 6.1 (a beta) with its WebGL renderer inside Electron; "Ghostty-class"
is marketing, and Ghostty is only a config importer. About 60,000 lines keep terminals alive in a
detached node-pty daemon, checkpoint scrollback every five seconds, restore exact screens after quit,
update or crash, and bring back scrollback plus `claude --resume <id>` after a reboot. Shell hooks
gate typed commands and report OSC 133 facts (no command blocks); each worktree has its own shell
history. Links get a popover, URLs wrapped inside TUI boxes are stitched, and a port scan ties dev
servers to worktrees. Hooks feed agent state to tabs, sidebar rows, Cmd-J and an experimental board.
The editor, settings, themes, plugins and languages trail Zed. Worth taking: structured hook events
into the rail (feeding #508 and #509); Orca's link details for #503; `claude --resume` and replayed
scrollback after a restart; attention order and unread in the rail; listening ports per project.

## 2. Features

### 2.1 The terminal engine

**What the user sees.** Terminal tabs and splits drawn on the GPU, ligatures for known ligature
fonts, inline images, kitty keyboard reporting, a 5,000-row scrollback by default.

**How it works.** The README's "Ghostty-class terminals with WebGL rendering" (`README.md` line 65)
means xterm.js with its WebGL renderer. The engine is `@xterm/xterm` 6.1.0-beta.303 with the
`webgl`, `fit`, `search`, `serialize`, `unicode11`, `web-links`, `image` and `ligatures` addons
(`package.json` lines 179-249). Ghostty appears only as a config importer (`src/main/ghostty`, 792
lines) and as the default theme's name, "Ghostty Default Style Dark"
(`src/shared/default-global-settings.ts` line 81). There is no libghostty in the tree. Orca carries
source patches to xterm and four addons, regenerated by `config/scripts/regenerate-xterm-patches.mjs`
(`docs/reference/xterm-patch-regeneration.md`): IME composition hooks, a `SortedList` fix, and
memory bounds for the image addon.

One xterm `Terminal` per pane, built in `src/renderer/src/lib/pane-manager/pane-dom-creation.ts`
with options from `pane-terminal-options.ts`: scrollback 5,000 rows (1,000 to 50,000,
`src/shared/terminal-scrollback-policy.ts`), `vtExtensions.kittyKeyboard` advertised, withheld
only on local Windows ConPTY (`terminal-keyboard-protocol.ts`), minimum contrast gated by the
background's luminance. The WebGL policy (`terminal-webgl-auto-policy.ts`) keeps WebGL on Linux
under Wayland or a hardware renderer and falls back to the DOM renderer on software rasterizers
(llvmpipe, SwiftShader, virgl), with a per-pane failure latch and context-loss recovery
(`pane-webgl-context-loss-policy.ts`, `pane-webgl-reattach.ts`). Inline images (Sixel, iTerm IIP,
kitty graphics) are on by default with a 32 MB decoded cache and an 8 MiB cap per sequence
(`terminal-inline-image-options.ts`; its own comment puts the worst case near 98 MB per pane).
Bytes reach the renderer over the `pty:data` IPC channel with `pty:ackData` credits for
back-pressure (`pane-terminal-output-ack-credit.ts`) and a per-pane output scheduler
(`pane-terminal-output-scheduler.ts`).

**Good and bad.** The guards are sensible: every xterm link provider is wrapped so a throw in one
cannot kill the renderer (`pane-dom-creation.ts`), and a search-decoration error is swallowed
rather than taking down the surface (`src/renderer/src/components/terminal-search-safe-find.ts`).
The history shows the cost. Between 2026-06-25 and 2026-09-25, 714 commits touched
`terminal-pane/` and `pane-manager/`; of the 915 that touched those two or `src/main/daemon`, 549
are `fix:` and 21 are reverts. Orca's first commit is 2026-03-16: 11,752 commits in six months,
about 60 a day across the repo.

**Size.** `src/renderer/src/components/terminal-pane` 64,100 lines (plus 133,800 test lines);
`src/renderer/src/lib/pane-manager` 13,700.

**Marley today: has most of it.** Zed's terminal is an alacritty grid drawn by gpui on the GPU, with
search and links. It lacks inline images. The vendored `alacritty_terminal` has the kitty keyboard
mode stack but Zed never turns `kitty_keyboard` on, and `crates/terminal/src/mappings/keys.rs`
sends LF for Shift+Enter, which Claude Code already reads as a newline.

### 2.2 Terminals that outlive the window: the daemon, scrollback on disk, resume

**What the user sees.** Cmd-Q, an update relaunch or an app crash leaves every shell and agent
running, and on relaunch each pane shows its current screen, modes included. After a reboot or a
daemon crash each pane shows up to 5,000 rows of its old scrollback above a fresh prompt in the same
cwd, and an agent whose session id Orca knows is relaunched with its resume flag (`claude --resume
<id>`, `codex resume <id>`, 17 agents in all; `getAgentResumeArgv` in `src/shared/agent-session-resume.ts`).
The docs page `model/session-restore.mdx` still tells users to re-run agents after a reboot.

**Process and wire.** `initDaemonPtyProvider` (`src/main/daemon/daemon-provider-init.ts`) adopts a
live daemon or forks a new one: a Node `fork()` of the Electron binary with `ELECTRON_RUN_AS_NODE=1`
and `detached: true`, cwd the userData directory, running `app.asar.unpacked/daemon-entry.js`; one
`ready` message over the fork's IPC channel, then `disconnect()` and `unref()`
(`daemon-launched-child-spawn.ts`, `daemon-launched-child.ts`). On Linux the fork is wrapped in
`systemd-run --user --scope`, so stopping the app's unit cannot take the daemon with it
(`daemon-cgroup-scope.ts`). The endpoint is `<userData>/daemon/daemon-v36.sock` beside `.token` and
`.pid` files, all mode 0600. The protocol version (36, `daemon-protocol-version.ts`) is part of the
name, so daemons of different versions coexist after an update and old sessions keep routing to the
daemon that owns them (`daemon-pty-router.ts`). The wire is NDJSON with a 16 MiB line cap: each
client opens a control socket and a stream socket, each starting with `hello {version, token,
clientId, role}`; 30 request types with ids and a 30-second timeout; writes, resizes and
pause/resume as fire-and-forget notifications; stream events `data`, `exit`, `dataGap` and a few
more. The daemon owns the node-pty handles. Each `Session` (`session.ts`) holds the PTY, an
`@xterm/headless` emulator, a pending-output buffer and the shell-ready barrier. Output is batched
for 2 ms, and a slow client stops the daemon reading the PTY. Main parses every byte again into its
own headless model (5,000 rows), then sends `pty:data` to the renderer with ack credits (512 KB per
PTY, 8 MB in all). A visible pane's bytes go through three VT parsers.

**Scrollback on disk.** Written by the Electron main process, not by the daemon, under
`<userData>/terminal-history/<worktree and session id>/`: `meta.json` (cwd, size, start time,
`endedAt`, exit code; a null `endedAt` marks a restorable session), `checkpoint.json` (the
SerializeAddon's ANSI for screen and history, rehydrate sequences, modes, OSC 8 ranges, cwd, title,
a generation and an output sequence number; `daemon-checkpoint-file.ts`) and `output.log` (magic
`OCKL`, a version and a generation, then frames: batch, output, resize, clear;
`terminal-history-log.ts`). A data event arms a one-shot five-second timer that appends the drained
output to the log. A full checkpoint (new generation, log reset) happens when the log would pass
5 MB, when the daemon's 2 MB pending buffer overflowed, on reattach, on quit and on sleep, and
otherwise at most once per 45 seconds (`daemon-pty-runtime-state.ts`). The daemon keeps only a
1,000-row live window (`daemon-session-scrollback-window.ts`: "a host owning 100+ terminals at full
depth retained ~1 GB of grid and was OOM-killed"), so the 5,000-row durable copy is rebuilt by
replaying disk plus the drained records through a scratch emulator. History is deleted when its
terminal closes or its worktree goes; nothing sweeps by age; nothing calls fsync.

**Restore.** Warm: the daemon takes a snapshot and attaches the new stream in the same synchronous
turn, so no byte falls between them; the renderer resizes to the snapshot's grid without a SIGWINCH,
writes the snapshot, drops live chunks the snapshot's sequence number already covers, then refits
(`terminal-pane/pty-connection/apply-reattach-payload.ts`). One viewer holds a session at a time.
Cold: replay the checkpoint and then the log into a scratch emulator (a generation mismatch or a
sequence gap discards the log), start a new shell at the recovered cwd and size, seed the daemon's
emulator before the first byte, and write the history into xterm under a replay guard so recorded
terminal queries do not answer into the new shell. A dead TUI's alternate screen is never restored:
its normal buffer comes back, followed by a reset of the alternate screen, kitty, mouse, focus and
paste modes (`src/shared/terminal-mode-reset-profiles.ts`). Then the resume command is typed
(`pty-connection/cold-restore-resume-startup.ts`), from session ids that hooks reported and that
were saved every 60 seconds and at quit.

**Hibernation** (experimental, off by default; report 01 has the rules). A finished background agent
idle for 30 minutes is stopped after a final checkpoint, the process killed, not paused; opening its
worktree cold-restores the pane and resumes the agent.

**Parking.** A worktree hidden for 30 seconds has its xterm instances disposed, WebGL renderer and
addons included, unless it is one of the four most recently hidden within five minutes
(`terminal-pane/terminal-hidden-view-parking.ts`, `components/terminal-parking-pass-candidates.ts`).
By Orca's own measurement a hidden pane held 2.5 MB of V8 heap at 5,000 rows of scrollback and 19 MB
at 50,000. While a pane is parked, main's own model keeps bells, titles and notifications working;
showing it again takes the warm-reattach path, a remount of about 170 ms.

**The shell-ready gate.** Orca starts an agent by typing its command into a login shell, and bytes
typed before the line editor owns the terminal are echoed twice, lost, or split into continuation
lines. For panes with a startup command, zsh, bash and fish print a private
`ESC ] 777 ; orca-shell-ready BEL` once the prompt is live; the daemon holds the command (sent as a
bracketed paste) and any early keystrokes until then, answers the DA1 query itself meanwhile, and
gives up after 15 seconds (`session-shell-ready-barrier.ts`).

**Good and bad.** Agents survive quit, update and crash with exact screens and modes, and a reboot
brings back scrollback, cwd, links and the conversation. For that, `src/main/daemon` alone runs to
28,600 lines plus 52,600 of tests, with 36 protocol versions shipped. `src/main/daemon/AGENTS.md`
records seven review rounds and twenty-three defects spent on one socket race. `DaemonPtyAdapter`
ends a 15-level class chain cut up to satisfy a line-count lint, and about 170 files in `src/main`
carry `@ts-nocheck`.
Durability depends on the UI process being alive: output produced while the app is closed reaches
disk only at the next reattach, and a burst over 2 MB while it is closed shrinks the durable history
to the daemon's 1,000-row window.

**A smaller version keeps:** a detached PTY host with one emulator per session, a token and an
exact-version handshake on a versioned endpoint, and an idle exit; an atomic snapshot (screen, modes,
cursor, pen, kitty flags) with a sequence number, then the live stream; back-pressure on the
producer; an append log and a compacted checkpoint written by the host, with fsync on compaction; the
cold-restore rules (scratch replay, drop a dead alternate screen, reset modes, recovered cwd, replay
guard); resume ids from hooks; a prompt-ready gate for typed commands. It drops multi-version
routing, main's second model, stream thinning and parking.

**Size.** About 60,000 non-test lines: the daemon 28,600, `src/main/ipc/pty` 11,600, the renderer's
`pty-connection/` 11,600, parking and hidden restore 7,250, transports 1,200.

**Marley today: lacks it.** Zed's terminals die with the app, and Zed brings a terminal back as a new
shell at its saved cwd with empty scrollback. Prong 2 gives Marley a host that already keeps
processes and scrollback alive: rustal-harness's tmux server, reached through display-only
terminals (C3). alacritty has no SerializeAddon, so a cold restore that keeps colours needs a grid
serializer of Marley's own, and a checkpoint would have to carry the block list too, since Orca
persists no command structure at all.

### 2.3 Shell integration and per-worktree shell history

**What the user sees.** Nothing, unless it breaks: commands typed by Orca land at a real prompt,
git status refreshes after a `git` command in a terminal, and the up arrow in a worktree's terminal
recalls that worktree's commands, not every worktree's.

**How it works.** Each shell gets a wrapper. zsh runs from a generated `ZDOTDIR`
(`src/main/shell-templates.ts`, `src/main/zsh-startup-wrapper-builder.ts`) whose first lines hand
`ZDOTDIR` back to the user's own directory before any of their files run, then source the user's
`.zshenv` and register a deferred hook. bash gets an rcfile (`src/main/daemon/daemon-bash-shell-ready-rcfile.ts`,
`src/main/providers/local-pty-shell-ready-bash-rcfile.ts`). fish gets an `--init-command`, which fish
runs after `config.fish` (`getFishShellReadyInitCommand` in `shell-templates.ts`). PowerShell gets
an OSC 133 bootstrap (`src/main/powershell-osc133-bootstrap.ts`). One environment variable,
`ORCA_SHELL_FEATURES`, carries a positive allowlist (overlay, history, markers, ready, identity,
startup) that the wrapper reads and unsets first, so nothing the user's config spawns inherits it
(`src/main/shell-startup-features.ts`).

The shells emit OSC 133 (C when a command starts, D with the exit code when it ends), an OSC 777
`orca-shell-start;<pid>` identity marker, and a ready marker: from zsh's `zle-line-init` (after zle
arms, chained to any user widget), from bash's prompt command, from fish's `fish_prompt` event. The
bash side is 179 lines of generated bash (`src/main/bash-prompt-command-composition.ts`) that turns
`PROMPT_COMMAND` into an array (native on bash 5.1 and later, emulated before), keeps `$?` intact
across the user's hooks, and chains the user's `DEBUG` trap under Orca's `__orca_osc133_preexec`.

The markers are used for four things. Startup commands wait for the ready marker. OSC 133;D fires
a window event that refreshes git status (`src/renderer/src/hooks/terminal-command-finished-event.ts`,
`right-sidebar/git-status-push-signal-refresh.ts`). OSC 133;C and D tell the foreground-agent
tracker that the shell has the terminal again (`terminal-pane/pane-foreground-agent-tracker.ts`).
An onboarding terminal checks a setup command's exit code (`onboarding/OnboardingInlineCommandTerminal.tsx`).
The renderer swallows OSC 133 so markers never paint (`terminal-pane/terminal-command-lifecycle.ts`).
There are no command blocks.

Per-worktree history is on by default (`terminalScopeHistoryByWorktree: true`). `injectHistoryEnv`
(`src/main/terminal-history.ts`) sets `HISTFILE` to
`<userData>/terminal-history/<hash of worktree id>/{zsh_history,bash_history}` beside a
`meta.json`, only when the user has not set `HISTFILE` themselves, and copies it to
`ORCA_HISTFILE` so the wrapper can restore it after macOS `/etc/zshrc` clobbers it. fish ignores
`HISTFILE`, so it gets `fish_history=orca_<hash>` (`src/main/fish-history-session.ts`).
`src/main/terminal-history-gc.ts` removes a worktree's history when the worktree goes.

**Good and bad.** The injection is careful about nesting (an Orca started from an Orca pane must
not write into the parent's worktree history), about frameworks (oh-my-zsh vi-mode's
`zle-line-init`), and about leaving the user's own files in charge. The issue numbers in its
comments (#11044, #11146, STA-4682) show that each of those rules arrived after a user saw a leak.
About 4,000 lines of injection code are split across the local, daemon and relay spawn paths.

**Size.** About 4,000 lines.

**Marley today: has most of it, more richly.** Marley's bash and zsh hooks (#463, #465) send DCS
frames with the command text, exit code, cwd, branch and a per-terminal nonce, and those frames
build blocks, which Orca does not have. fish is TICKET-466. Marley waits for Zed's startup
handshake before it types an agent's name (`crates/marley_workbench/src/agents.rs` `start_cli`).
It lacks per-worktree history.

### 2.4 Links: files, URLs, localhost and ports

**File paths.** A custom xterm link provider (`terminal-pane/terminal-link-handlers.ts`,
`createFilePathLinkProvider`) finds path candidates with `:line:col` across soft-wrapped and
hard-wrapped lines, resolves them against the pane's cwd (tracked from OSC 7, `parse-osc7.ts`),
checks that they exist in one batched call with a cache (`terminal-path-existence-batch.ts`,
`terminal-path-exists-cache.ts`; over SSH the probe is remote), and only then underlines them. A
link opens in Orca's editor, or in the HTML preview for `.html`; Shift plus the modifier opens it
with the system default. A mouseup fallback retries the hit test when xterm misses a wrapped row.

**Web links.** The `web-links` addon plus Orca's own hit tests: URLs that a TUI hard-wraps inside a
box (`hard-wrapped-terminal-http-links.ts` and `edge-wrapped-terminal-http-links.ts` recognise the
`│ ┃ ║` frame characters and stitch the rows back together; Ink-based CLIs such as Claude Code wrap
long lines themselves, so xterm sees separate rows with no wrap flag),
and OSC 8 hyperlinks (`terminal-osc-link-routing.ts`). A plain click opens a small popover
(`src/renderer/src/components/link-actions/LinkActionPopover.tsx`): Orca Browser, System Browser,
and Copy link, which copies the hidden OSC 8 target. Ctrl-click opens at once, Shift+Ctrl-click takes
the other destination (`resolveModifierRouting` in `src/renderer/src/lib/http-link-routing.ts`),
middle-click opens. The default destination is the system browser (`openLinksInApp: false`), and
the first link click asks once where links should open (`link-routing-preference-dialog.tsx`).
Links printed in SSH panes stay system-browser only unless the remote host is capability-verified.

**Handles.** The `orca` CLI prints `term_…` and `task_…` ids; the terminal turns them into links that
focus that terminal or orchestration task (`terminal-handle-links.ts`,
`terminal-orchestration-task-links.ts`).

**Ports.** While the window is visible the renderer asks main for a port scan every 30 seconds
(`src/renderer/src/components/ports/WorkspacePortScanner.tsx`). Main reads `/proc/net/tcp` and
`tcp6` plus each process's `fd`, `cwd` and `cmdline` on Linux, `lsof` on macOS and `netstat` on
Windows, in a worker (`src/main/ports/local-workspace-platform-port-scanner.ts`,
`port-scan-command-worker-entry.ts`), and attributes each listener to a worktree by its cwd, or
failing that by a worktree path in its command line (`local-workspace-port-attribution.ts`).
`AdvertisedUrlWatcher` (`src/main/ports/advertised-url-watcher.ts`, `advertised-url-parsing.ts`)
reads every PTY's output line by line (a 4 KB carry per PTY so URLs and escapes split across chunks
survive, ANSI and OSC stripped), caches the advertised origin per worktree and port, and keeps it
only while a listener with that port is seen, so Vite's `Network: https://…:3001/` wins over a bare
`http://localhost:3001`. Ports show on the worktree's sidebar card behind a plug icon with Open in
Browser, Copy and Stop (kills the PID) (`sidebar/WorktreeCardPorts.tsx`), in a status-bar segment
and in a right-sidebar Ports tab.

**Localhost labels** (opt-in, `localhostWorktreeLabelsEnabled: false`). Main runs an HTTP and
WebSocket reverse proxy on a random loopback port (`src/main/localhost-worktree-label-proxy.ts`). A
local URL whose port belongs to a worktree opens as
`http://<worktree-slug>.orca.localhost:<proxy-port>/…`, with `<project>-main` for a primary checkout
(`src/shared/localhost-worktree-labels.ts`). The address bar then names the worktree, and because
browsers key cookies and `localStorage` by host and not by port, two worktrees' dev servers stop
sharing a login.

**Good and bad.** The popover is a fair answer to "which browser", the stitching makes URLs in
wrapped agent output clickable, and checking a URL against a live listener stops stale URLs from
being offered. The port scan walks every process's fd table every 30 seconds, which is fine on a laptop
and not free on a busy box.

**Size.** Link code in `terminal-pane/` 3,400 lines; ports 2,400 in main plus 900 of UI; the label
proxy and routing 700.

**Marley today: has part; #503 is queued.** Zed's terminal finds paths and URLs, opens paths in the
editor and URLs in the system browser on Ctrl-click; Marley's T2 plans block-scoped path
resolution. TICKET-503 routes local URLs to a Browser tab and offers the URL a dev server printed.
Marley has no port scan, no per-project port list and no labelled hostnames.

### 2.5 Which agent runs in a terminal, and what it is doing

Report 01 covers the hook server, the per-agent rules and the attention policy. What matters for
the terminal:

- **Sources.** Hooks that Orca installs in each agent's global config (for Claude Code in
  `~/.claude/settings.json`: SessionStart, UserPromptSubmit, Stop, StopFailure, SubagentStart,
  SubagentStop, TeammateIdle, PreToolUse, PostToolUse, PostToolUseFailure, PermissionRequest,
  PostCompact, SessionEnd; `src/main/claude/hook-settings.ts`). The hook script pipes the hook's
  JSON with `curl` to `http://127.0.0.1:$ORCA_AGENT_HOOK_PORT/hook/<agent>` with a token header
  and the pane's identity from environment variables every PTY is given (`ORCA_PANE_KEY`,
  `ORCA_TAB_ID`, `ORCA_AGENT_LAUNCH_TOKEN`, `ORCA_WORKTREE_ID`;
  `src/main/agent-hooks/hook-post-command.ts`). Then OSC titles (agent CLIs animate the title while
  they work; `src/shared/agent-title-status.ts`), foreground-process inspection, and Orca's own
  launch intent. Precedence, per pane: live hook, process, title, completed hook, sleeping record,
  launch intent, sibling pane (`src/renderer/src/lib/tab-agent-from-signals.ts`). Orca merges its
  hooks into the user's own `~/.claude/settings.json`; Marley's plugin route leaves that file alone.
- **On the tab.** The leading icon is the agent's glyph with a state dot, or an amber bell for an
  unread completion (`tab-bar/TerminalTabLeadingIcon.tsx`, `terminal-tab-activity-status.ts`, which
  reuses the sidebar's status vocabulary). The title can be the agent's conversation name (Claude's
  custom title, Codex's thread name); a manual rename wins.
- **Rules worth copying.** A Claude `PermissionRequest` stays "waiting" through the next "working"
  event unless the approved tool resumes, and `AskUserQuestion` counts as a question, not a
  permission (`src/main/agent-hooks/server/server-claude-status-rules.ts`). A pane whose PTY is
  alive but whose hooks went silent reads "unverifiable", never idle. Rows restored from disk
  (`last-status.json`, a 7-day window) carry `restoredUnconfirmed` and never count as live.

**Marley today: has part.** The rail recognises an agent from the terminal's foreground command and
calls it waiting after 2 seconds without output or on a bell (`crates/marley_agent/src/marley_agent.rs`,
`agent_status`). The Claude Code plugin's hooks (Notification for `permission_prompt` and
`idle_prompt`, and Stop) return a `terminalSequence` that makes Claude Code write OSC 777 to its own
terminal (`crates/marley_workbench/claude_plugin/marley/hooks/notify.sh`). No prompt, tool, last
message or session id reaches Marley.

### 2.6 Smaller terminal features

- **Search.** Cmd-F over the scrollback with case and regex toggles and a match counter, the stock
  search addon (`src/renderer/src/components/TerminalSearch.tsx`, 230 lines). Marley has it.
- **Copy mode.** None. Orca has no keyboard selection mode; neither has Zed.
- **Copy without the agent's gutter.** On by default (`terminalCopyTrimsGutter`), a copied
  selection loses the run of leading spaces that every non-blank line shares, so text copied out of
  Claude Code's indented replies pastes flush left while relative indentation survives
  (`src/shared/terminal-selection-gutter.ts`, 60 lines). Marley lacks it.
- **Copy Context and Fork Agent Session** (terminal context menu). Both serialize the last 800 rows,
  strip escapes, cap at 36,000 characters keeping the newest, and fence the text
  (`src/renderer/src/lib/agent-session-fork-context.ts`). Copy Context puts it on the clipboard.
  Fork creates a new worktree from the pane's branch and starts an agent there with the transcript
  as its first prompt (`terminal-pane/terminal-agent-session-fork.ts`). Marley lacks both; its MCP
  `terminal_read` gives the text to agents, not to the user.
- **Protected multi-line paste.** When a pane's agent is known, a multi-line paste is bracketed even
  if the terminal never saw DECSET 2004, because a bare CR would submit the agent's draft and some
  shells never announce bracketed paste at all (`terminal-pane/terminal-agent-paste-bracketing.ts`).
  Marley's rich input brackets only "when the agent asked for it".
- **OSC 52.** TUI clipboard writes allowed by default with a one-time notice (`osc52-clipboard*.ts`).
  Zed handles OSC 52 too.
- **Quick Commands.** A saved command (label, text, whether to press Enter) or a saved agent prompt
  (agent plus prompt), global or per repo, run from a split button on the tab bar (new tab) or the
  context menu (typed into the current terminal) (`src/shared/terminal-quick-command-types.ts`,
  `components/terminal-quick-commands`, 1,100 lines). Zed's tasks cover saved commands; Marley has
  no saved agent prompts.
- **Floating workspace.** A global panel, toggled with Ctrl+Alt+A, dragged and resized over the
  window, with its own terminal, browser and markdown-note tabs outside any worktree; it uses the
  synthetic worktree id `global-floating-terminal` (`components/floating-terminal`, 5,200 lines).
  Zed's terminal dock and Hyprland's scratchpads do the same job for Marley.
- **Pane chrome.** Splits inside a terminal tab, a title per pane (Set Title…), expand and collapse
  one pane, equalize sizes, dim inactive panes, focus follows mouse (opt-in,
  `pane-manager/focus-follows-mouse.ts`), right-click paste, hide the mouse while typing. Zed has
  each of these; renaming a terminal covers the pane title.

### 2.7 Tabs, panes and splits

**What the user sees.** Drag a tab onto a pane's edge to split, nest splits without limit, and
split a terminal tab again inside itself. Every worktree keeps its own layout, swapped whole when
you switch worktrees.

**How it works.** Two levels. Tab groups form a split tree per worktree, `{leaf | split, direction,
ratio}` (`src/shared/tab-types.ts`, `TabGroupLayoutNode`); the drop target is VS Code's shape (the
middle 80 percent merges, the outer thirds split left or right, otherwise up or down;
`src/renderer/src/components/tab-group/tab-drop-zone.ts`). Inside a terminal tab the pane manager
keeps a DOM flex tree serialized the same way (`terminal-pane/layout-serialization.ts`), ratios

### 2.8 Session restore

**What the user sees.** Quit and relaunch, and every worktree, split, tab, scrollback, open file
(unsaved edits included), browser tab and the focused view come back.

**How it works.** Almost everything lives in one JSON file, `<userData>/orca-data.json`
(`src/main/persistence/loading-store/user-data-path.ts`), with the GitHub cache and the top-level
view in sidecars (`orca-github-cache.json`, `active-view.json`, `src/main/active-view-preference.ts`).
`WorkspaceSessionState` (`src/shared/workspace-session-state-types.ts`) holds the tabs per worktree,
the terminal layouts, serialized scrollback per pane (`buffersByLeafId`, shared with paired peers,
and `localOnlyScrollbackByTabId` for ordinary parks), open editor files with any unsaved draft and
the disk signature it was based on, so a restore can detect a conflicting change on disk, browser
tabs and URL history, the active tab, type and group per worktree, last-visit times for Cmd-J, the
SSH targets to reconnect, remote PTY session ids, and the resume records of sleeping agents. On
quit, `beforeunload` captures the terminal buffers, the resume records and the dirty drafts and
stages them through one synchronous call to main (`src/renderer/src/app-shell/shutdown-checkpoint-persist.ts`);
resume records are also captured every 60 seconds, so a hard kill loses at most a minute
(`use-app-session-persistence.ts`). The processes themselves survive through the daemon (2.2).

**Good and bad.** Unsaved editor drafts survive with conflict detection. The whole session is one
multi-megabyte JSON document, and `src/main/persistence*` is dominated by migrations (test files
named `persistence-pane-identity-migration`, `persistence-cohort-and-identity-migration`, and a
hundred more).

**Marley today: has part.** Zed restores workspaces, panes, editors with unsaved buffers, and
terminals at their saved cwd (`crates/terminal_view/src/persistence.rs`), as new shells with empty
scrollback.

### 2.11 The agent dashboard and the pop-out window

**What the user sees** (experimental, off by default: `experimentalAgentDashboardPopout`). A board of
agent cards in Needs You, Working, Done and an optional Idle column. A finished card stays green
until acknowledged, then goes grey (`src/shared/dashboard-snapshot.ts`,
`dashboardCardDisplayState`). It opens as a drawer in the main window or as its own window. A click
on a card opens a live terminal of that agent in a dialog, where you can type, so a permission
prompt is answered without leaving the board.

**How it works.** The main renderer owns the store, derives a structured-clone-safe
`DashboardSnapshot` and sends it on `dashboard:publishSnapshot`. Main validates it
(`src/main/ipc/dashboard-payload-validation.ts`), keeps the last one for a pop-out that mounts late,
and forwards it on `dashboard:snapshot` (`src/main/ipc/dashboard-popout.ts`). The pop-out is a
second BrowserWindow (`src/main/window/dashboard-popout-window.ts`) with its own React root and
store (`src/renderer/src/popout.tsx`); acknowledge, reveal, spawn and sleep go back on
`dashboardPopout:*` channels. The terminal dialog connects with `terminalPreview:connect`, which
returns a snapshot and a stream with an atomic boundary between them; input, acks and fit go over
`terminalPreview:*`; the dialog claims the PTY's size and the main window's pane parks until it
closes (`src/main/ipc/terminal-preview.ts`, `dashboard-popout/AgentTerminalPreview.tsx`).

**Good and bad.** Relaying a presentational snapshot through main keeps the pop-out simple and
lets the main window stay the only owner of state. Running a second React app for one board is
heavy, and the feature is still behind a flag.

**Size.** `dashboard/` 3,800 lines, `dashboard-popout/` 3,100, main IPC and window 700.

**Marley today: lacks it.** #508's approvals inbox is the Needs You column; gpui opens a second
window cheaply, and Zed's display-only terminal can mirror a PTY for the dialog.

### 2.13 The editor and agents writing files

**What the user sees.** Monaco tabs with a dirty dot. Autosave is a setting, off by default
(`editorAutoSave: false`, `src/shared/default-global-settings.ts` line 50; delay 1,000 ms, clamped
to 250-10,000). When an agent rewrites a file that has unsaved edits, an amber banner offers
Compare, Reload from Disk (with an eight-second undo) and Keep My Edits. A Changes view flips a tab
to a HEAD-versus-working-tree diff whose right side stays editable.

**How it works.** `@parcel/watcher` runs in a forked Electron-as-Node child with a crash fuse
(`src/main/ipc/parcel-watcher-child-launch.ts`); main batches events (150 ms trailing, 500 ms
maximum, `src/shared/filesystem-watch-batch-window.ts`) and sends `fs:changed`; on SSH hosts the
relay runs the same supervisor. In the renderer (`src/renderer/src/hooks/editor-external-watch-event-reconciliation.ts`)
a clean tab reloads after 75 ms, only when visible (hidden tabs are marked stale), and the new text
enters Monaco as an undoable edit, a pure append as an end-of-file insert that keeps the viewport.
A dirty tab keeps its buffer, is marked changed on disk, and autosave pauses for it. Orca tags its
own writes (`editor-self-write-registry.ts`, 750 ms locally, 3 s remote) and re-reads the disk to
tell its own write from an agent's. Unsaved drafts persist across restarts with a disk signature and
are re-checked on launch. The save itself is a plain `writeFile(path, content, 'utf-8')`
(`src/main/ipc/filesystem/filesystem-write-handlers.ts`) with no check of the file's current state.

**Good and bad.** The dirty-tab rules and the banner are right for agents that edit files while you
read them. Three faults: an agent's write that lands within the watcher latency before an autosave
is overwritten silently, since the save compares nothing; the watcher ignores `build`, `target`,
`dist` and similar at any depth, so an open file there never reloads; and Cmd-Z undoes the agent's
change, which autosave then writes back. The docs promise save-on-blur and no dirty dot; the code
has neither. Monaco runs with all TypeScript diagnostics off (`src/renderer/src/lib/monaco-setup.ts`
calls it "a viewer/diff surface, not a type checker"); go-to-definition is a text search.

**Size.** `components/editor` 45,700 lines; autosave and external sync 3,600; the watcher in main
7,000, shared with the explorer and git status.

**Marley today: has it, better.** Zed's editor with LSP, its own file watching and reload of clean
buffers, conflict handling on save (it checks the file's mtime), and hot exit.

### 2.15 Files and images dropped on an agent

**What the user sees.** Drop files from the file manager onto an agent's terminal and their paths
appear at its prompt; drop an image and Claude Code or Codex attaches it; paste a screenshot with
Ctrl+V and the same happens, over SSH too.

**How it works.** One capture-phase listener in the preload (`installNativeFileDropHandlers`,
`src/preload/preload-runtime-support.ts` line 92) takes every native drop, gets real paths with
`webUtils.getPathForFile`, finds the target from `data-terminal-tab-id` and
`data-terminal-pane-leaf-id` on the event path, caps a drop at 256 paths, and relays it through main
as `terminal:file-drop`. Image files (by extension) whose paths hold no shell metacharacters go in
raw, inside a forced bracketed paste, because that is how Claude Code and Codex recognise an image
attachment; other paths are shell-quoted with a trailing space; nothing presses Enter
(`terminal-pane/terminal-drop-path-writer.ts`, `terminal-drop-image-path.ts`). On an SSH worktree
the files are first uploaded to `<worktree>/.orca/drops/` and the remote paths pasted
(`fs:resolveDroppedPathsForAgent`, `src/main/ipc/filesystem-mutations.ts`). A clipboard image is
written to `orca-paste-<ts>-<uuid>.png` in the temp directory, or over SFTP on the remote, and its
path pasted the same way (`terminal-clipboard-paste.ts`, `src/main/window/clipboard-image-temp-file.ts`).
Drags from Orca's own explorer carry a private MIME type and paste host paths directly. Review notes
go to an agent only after the runtime reports its TUI idle, as a bracketed paste, then Enter
(`src/renderer/src/lib/active-agent-note-send-delivery.ts`).

**Good and bad.** Raw image paths in a bracketed paste is the detail that makes attachments work.
Nothing is cleaned up: temp PNG files accumulate, and `.orca/drops/` grows inside the worktree without an
entry in `.git/info/exclude`, so an agent's `git add -A` can commit it. SVG, ICO and BMP count as
images though the Claude API takes only PNG, JPEG, GIF and WebP. The docs' "drop an image into the
Markdown editor" does not exist; the drop opens the image as a tab.

**Size.** Drop 1,650 lines, paste 2,100, main clipboard 1,250.

**Marley today: has most of it.** Zed pastes dropped files and project-panel selections as quoted
paths (`crates/terminal_view/src/terminal_view.rs`, `add_paths_to_terminal`, which shell-quotes each
path and prefixes a space), forwards Ctrl+V to the program when the clipboard holds an image so
Claude Code reads the clipboard itself, and refuses drops on remote projects. Marley adds Attach File
(#479) and rich input (#481). Missing: raw image paths so a quoted path does not defeat Claude Code's
attachment check, and the upload for remote terminals.

### 2.16 Dictation

**What the user sees.** Settings → Voice (off by default, no model chosen): microphone, Toggle or
Hold, and model downloads. Cmd-E or Ctrl-E starts and stops; a Listening pill shows level, partial
text and Stop. Text lands in whatever had focus when dictation started.

**How it works.** sherpa-onnx 1.12.37's native addon runs in a `worker_threads` Worker inside the
Electron main process (`src/main/speech/stt-session-start.ts` line 127), CPU only, kept warm for an
hour. Models (Parakeet v3, about 670 MB int8, recommended; Parakeet v2 and JA, Whisper Tiny,
SenseVoice, four streaming Zipformers, Paraformer) download from pinned Hugging Face revisions with
per-file SHA-256 into `<userData>/speech-models/<id>/`. The renderer captures with `getUserMedia`
into a `ScriptProcessorNode`, sends each buffer over `speech:feedAudio`, and the worker resamples to
16 kHz. Streaming models finalize an utterance after trailing silence; offline models decode in
30-second chunks split at the quietest point (after a 2 GiB allocation crashed the app, #7925).
The cloud path uploads one WAV to OpenAI's `/v1/audio/transcriptions` at stop. Delivery
(`dictation-insertion-target.ts`): into a terminal as a paste, bracketed if the program enabled
bracketed paste, never with Enter, so Claude Code receives each final segment in its prompt; into
text fields and the rich editor through input events.

**Good and bad.** Offline models, pinned and hashed, are the right defaults. A native crash in
sherpa takes down Electron's main process (the file watcher is isolated in a child; speech is not),
`ScriptProcessorNode` on the renderer thread drops audio when the UI stalls, moving focus mid-dictation
discards the text, and the shortcut takes Ctrl-E from readline and Claude Code on Linux while
dictation is enabled.

**Size.** About 6,300 lines.

**Marley today: has it.** Voxtype, the dictation daemon Omarchy ships, types into the focused window;
the agent bar's microphone runs `voxtype record toggle` and follows `voxtype status --follow`
(`crates/marley_workbench/src/voice.rs`). Nothing to take.

### 2.18 Settings

**What the user sees.** Cmd-, opens a settings page inside the main window: eight groups (AI
Capabilities, Set Up, Workflows, Interface, Remote Hosts, Privacy and Security, Advanced,
Experimental) and a pane per project, with a search box. Feature surfaces jump straight to their
setting: the terminal link popover's gear, for one, scrolls to the setting and highlights it.

**How it works.** Search is not generated. About 70 hand-written `*-search.ts` files (7,400 lines)
list each setting's title, description, keywords, Cmd-J keywords and target section;
`scoreSettingsSearch` (`src/renderer/src/components/settings/settings-search.ts`) ranks exact over
prefix over substring, weighting pane titles above setting titles above descriptions above
keywords, with no fuzzy match, and each row repeats its text in a `SearchableSetting` wrapper that
hides it on a miss. The same entries feed Cmd-J. In a translated UI the English terms still match.
Deep links go through `openSettingsTarget({pane, sectionId, repoId})`, which scrolls, highlights for
three seconds, and waits up to five for rows that load late. All settings are one object with about
230 fields inside `orca-data.json`, written atomically after a one-second debounce with five
rotating backups; secrets are encrypted with Electron's `safeStorage`. There is no hand-editable
settings file, no export or import, no reset-all, and migrations are one-off `migratedX` flags under
a `SCHEMA_VERSION` still at 1. The checked-in per-repo file is `orca.yaml`
(`src/shared/orca-yaml.ts`, keys read in `src/main/hooks.ts`): `scripts.setup` and
`scripts.archive`, `setupAgentStartupPolicy`, `issueCommand`, `defaultTabs`, `environmentRecipes`,
`worktree.sharedDirectories`. A script runs only after the user approves it, and the approval is
tied to the script's hash (`ensure-hooks-confirmed.ts`). `orca.yaml` cannot set editor, terminal or
appearance options.

**Good and bad.** Hash-bound approval of repo scripts is the right model for worktree setup
scripts. The hand-kept search index drifts from the rows it describes, and `settings.mdx` already
promises an accent colour and a density setting that do not exist.

**Size.** `components/settings` 72,500 lines in 484 files; main-process settings 2,600; the
persistence layer 15,500.

**Marley today: has it, better.** Zed has `settings.json`, per-project `.zed/settings.json`, a
settings UI with search and `zed://settings/<path>` links (`crates/settings_ui/src/settings_ui.rs`).
It lacks approval of repo-supplied scripts, which Marley will need once a worktree agent runs a
repo's setup (#510).

  chord, a list, or `null` to unbind, with per-platform sections. One chord per binding, no key
  sequences, no context conditions (the scopes are fixed), no file watching; conflicting user
  bindings are dropped on load. 127 actions (88 fixed plus 39 "New <agent> tab"). The Shortcuts pane
  filters all, modified, unassigned and conflicts, records chords with global shortcuts paused, and
  refuses a conflicting chord. No VS Code, JetBrains, Vim or Emacs presets and no Vim mode; plugins
  bind only their own commands. Zed's keymaps (base keymaps, contexts, sequences, Vim mode) are far
  ahead; nothing to take.
- **UI themes.** System, Dark or Light only: one fixed palette of about 110 CSS variables per mode
  in `src/renderer/src/assets/main.css`. No theme files, no accent colour. Zed is far ahead.
- **Terminal themes.** 30 built-in themes (`src/renderer/src/lib/terminal-themes/`), chosen separately
  for dark and light mode; one global set of colour overrides that picking a theme erases; up to 200
  imported themes that cannot be renamed or deleted. Orca answers DEC 2031 and OSC 10/11 colour
  queries so TUIs follow light and dark. The Ghostty importer (`src/main/ghostty`, 792 lines) reads
  `config.ghostty` or `config` from the XDG and platform folders and maps about 24 keys (palette, font,
  cursor, opacity, padding, cell height); it refuses `theme = light:X,dark:Y`, ignores `config-file`
  includes, and takes the last `font-family` where Ghostty uses the first. The Warp importer
  (`src/main/warp-themes`) parses Warp's YAML themes in a worker. Zed's terminal follows the editor
  theme, with `terminal.*` overrides.
- **Icons.** No icon themes: a fixed table of about 173 extensions and 73 file names mapped to
  monochrome Lucide icons (`file-type-icons.ts`). Three app icons (Classic, Watercolor, Blue); on
  macOS the installed `.app` icon is rewritten through `osascript`, on Linux only the window icon
  changes. Zed has icon themes as extensions.
- **Languages.** i18next with seven UI languages (English, Simplified Chinese, Korean, Japanese,
  Spanish, French and System), 13,500 `translate(key, englishFallback)` calls with hashed keys
  (`auto.<path>.<hash>`), machine-translated through Google's unofficial endpoint and patched by 12,000
  lines of fix-up scripts; Spanish is 17 percent missing. Plugins can add a language but not patch
  one. Zed has no UI translation; Marley does not need one.

**Size.** Keybindings 6,000 lines with the UI; themes about 7,000 with both importers; i18n 800 of
runtime plus 106,700 lines of translation JSON.

**Marley today: has what matters.** Zed's keymaps, themes and icon themes. The one gap is a Ghostty
config import for the terminal's font and palette; on Omarchy the desktop theme already sets both.

### 2.20 Plugins and the marketplace

**What the user sees** (experimental; `pluginSystemEnabled: false` by default,
`src/shared/default-global-settings.ts` line 195). Settings → Plugins lists installed plugins with a
status (Running, Enabled, Needs review, Disabled, Blocked, Error, Invalid), logs, roll back, remove
and an enable switch; an install dialog (a local folder or a git `url#ref`), a marketplace browser,
and a development mode that loads folders from disk. Plugin panels show as icons in the right
sidebar; plugin commands show in Cmd-J and in Shortcuts.

**How it works.** A plugin is a folder or git repo with `orca-plugin.json`
(`src/shared/plugins/plugin-manifest.ts`, a zod schema): id, publisher, version, `engines.orca`,
`pluginApi: 1`, `main` (a Node entry file), `capabilities`, and `contributes` with exactly seven
keys: `panels`, `commands`, `events` (`worktree.created`, `worktree.removed`, `agent.status.changed`),
`languagePacks`, `keybindings` (own commands only), `vmRecipes` (shell commands for the Cloud VM
runner) and `agents` (validated, then read by nothing). Themes, icon themes, terminal themes and
skills are refused. A marketplace is any git repo with `orca-marketplace.json`; the official
`github.com/stablyai/orca-plugins#main` is added and cannot be removed. Install is
preview-then-install at the same commit (it refuses if the commit moved), copies the tree without
`.git` into `<userData>/plugins/<publisher>.<id>/<sha256>/`, never runs install scripts, keeps the
current and one previous version for rollback, and records provenance and a lock file
(`src/main/plugins/plugin-install*.ts`). Updates are manual. Plugin code runs as a forked Node
process (`ELECTRON_RUN_AS_NODE`, minimal environment, at most five at once, stopped after five idle
minutes, marked errored after three crashes) with an API of 13 methods behind seven capabilities
(`src/shared/plugins/plugin-host-api.ts`): read the focused worktree's context, send text to a
terminal by id, show a notification, key-value storage and secrets, subscribe to events. Capabilities
only limit calls into Orca; the process itself can touch the file system, the network and child
processes, and the consent dialog says so. Panels are `sandbox="allow-scripts"` iframes with inline
HTML under a CSP that forbids the network (`src/shared/plugins/plugin-panel-shell.ts`); they cannot
talk to their own plugin's code. Consent is a hash of the capability set, a has-code flag and, for
keybindings, VM recipes and agents, the tree hash. A kill list (`https://onorca.dev/plugins/kill-list.json`,
unsigned) blocks by id.

**What the marketplace lists.** Eight plugins, all by stablyai at `v1.0.0`
(`/srv/stacks/orca-refs/orca-plugins/orca-marketplace.json`, one commit): two app themes, a skills
pack, an icon theme and a terminal theme, all five hidden because their categories are unsupported
(`UNSUPPORTED_MARKETPLACE_CATEGORIES`, `src/shared/plugins/plugin-marketplace.ts`); a 22-string
Brazilian Portuguese pack; Multipass VM recipes; and the bundled navigation-shortcuts plugin, three
command aliases.

**Good and bad.** The supply chain is careful: pinned commits, content hashes, immutable versions,
one-step rollback. Everything else is thin: no sandbox for code, an API with no files, editor, git or
status bar, panels that cannot reach their own code, and an official index that advertises five
plugins nobody can install. It all arrived in one commit (#8549, 2026-07-27).

**Size.** About 15,900 lines: `src/main/plugins` 7,400, `src/shared/plugins` 2,700, the settings UI
3,400, the rest wiring.

**Marley today: has a better base.** Zed's WebAssembly extensions (languages, grammars, language
servers, themes, icon themes, slash commands, context servers) with a registry and auto-update.
Nothing here to take except, perhaps, HTML panels for agent-built tools, and Zed has no panel
extension point for those.

## 3. Bring to Marley

Ranked by what each buys Marley against what it costs. S is a day, M a few days, L a week or more.

1. **Structured agent events from the Claude Code plugin.** Prompt, tool in flight, last message,
   session id; states working, needs permission (with the tool and its input), question, done,
   interrupted, stale.
   - *Why.* The rail guesses from output silence (2 s) and the bell, so it cannot tell a long think
     from a permission prompt, and it shows nothing of what an agent is doing. Orca's rows
     (conversation name or prompt, then the tool in flight or the last reply, then the time) come
     from hooks, and the same events feed its ordering, notification text, resume and board (2.5,
     2.10).
   - *Lands in.* The plugin's `hooks.json` grows SessionStart, UserPromptSubmit, PreToolUse,
     PostToolUse, PostToolUseFailure, PermissionRequest, Stop, StopFailure, SubagentStart,
     SubagentStop, PostCompact and SessionEnd. Two transports: keep today's pane-bound trick, a hook
     answer whose `terminalSequence` Claude Code writes to its own terminal (#482 found it limited to
     OSC 0, 1, 2, 9, 99, 777 and BEL, and dropped in print mode), carrying a Marley OSC 777
     subcommand with a short JSON payload parsed beside `notifications.rs`; or POST the hook JSON to
     `marley_mcp`'s loopback server with the endpoint file's bearer and a terminal id exported into
     the PTY's environment, as Orca does with `ORCA_PANE_KEY` and a token header. `marley_fleet`
     folds the events per terminal; `marley_rail` draws two lines per agent row.
   - *Size.* M.
   - *Hard.* The state rules: a PermissionRequest stays pending until the same `tool_use_id` reaches
     PostToolUse or the turn ends; AskUserQuestion is a question, not a permission; a stream silent
     for 30 minutes on a live PTY reads "unverifiable", not idle; rows restored from disk never count
     as live.
   - *Sprint.* Feeds #508 (the inbox needs PermissionRequest's tool and input, not only
     Notification's `permission_prompt`, and a clear rule for when an entry leaves) and #509 (turn
     boundaries are UserPromptSubmit and Stop).

2. **TICKET-503, with Orca's details** (queued).
   - *Why.* Orca already hit the problems #503 will hit.
   - *Include.* Stitch URLs that a TUI wrapped itself, inside a box frame or at the terminal's edge,
     before matching (`hard-wrapped-terminal-http-links.ts`, `edge-wrapped-terminal-http-links.ts`);
     follow OSC 8 targets; a plain click that offers Browser tab, system browser and Copy, with
     Ctrl-click opening the default at once and Shift+Ctrl-click the other; ask once, on the first
     click, which should be the default; find the dev server's URL by scanning output line by line
     with a carry, so an escape or a URL split across reads survives, and offer it only while
     something listens on that port; open `0.0.0.0` and `::` as `127.0.0.1` and `::1`; leave URLs
     from SSH terminals to the system browser.
   - *Size.* S to M, inside #503.

3. **Claude Code sessions resumed after a Marley restart.**
   - *Why.* Today a restart ends every terminal agent. `claude --resume <id>` brings the conversation
     back; Orca does this for 17 agents on every cold restore (2.2).
   - *Lands in.* The session id from item 1's SessionStart, kept per terminal: in the terminal's row
     of Zed's workspace database (`crates/terminal_view/src/persistence.rs` keeps the cwd; a
     touchpoint) or a Marley table keyed by item id. On restore, after the startup handshake,
     `start_cli`'s path types `claude --resume <id>` instead of `claude`. For the scrollback: at quit,
     save each terminal's last few thousand rows with their colours and write them into the restored
     terminal above the new prompt, marked as restored.
   - *Size.* M: resume is S; the scrollback is the rest, because alacritty has no serializer.
   - *Hard.* Capture at quit and every minute, as Orca does, so a crash loses at most a minute; never
     resume one session twice (Orca tags each record with where it was captured); blocks inside the
     replayed rows are restored from saved metadata or dropped. Keeping the processes themselves
     alive belongs to the harness (prong 2, C3), and Orca's daemon shows what that client must do: an
     atomic snapshot with a sequence number, then the live stream; one viewer at a time sets the size;
     the host, not the UI, writes the history.
   - *Sprint.* Not queued.

4. **Attention order and unread in the rail and its switcher.**
   - *Why.* With several agents the first question is who needs you. Orca's Smart order: needs you,
     done and unseen, working, unverifiable, idle; a row stays unread until its pane is seen; Cmd-J
     opens with the six recent agents, jumped to by digit.
   - *Lands in.* A sort key and an unread flag per row in `marley_rail`, fed by `marley_fleet`'s
     attention model; a needs-you-first section with digit shortcuts in `rail_switcher.rs`.
   - *Size.* S to M, after item 1.
   - *Hard.* Acknowledge per turn (Orca compares the turn's start time with the last acknowledged
     one), so repeated pings of the same state do not light a row again.
   - *Sprint.* Partly #508.

5. **Ports per project in the rail.**
   - *Why.* Nothing shows which dev server belongs to which worktree agent. Orca lists each
     worktree's listening ports with Open, Copy and Stop, and keeps the URL the server printed.
   - *Lands in.* A pure `marley_ports` crate that reads `/proc/net/tcp` and `tcp6`, maps socket
     inodes to PIDs through `/proc/<pid>/fd`, and attributes a listener to the project whose root
     holds `/proc/<pid>/cwd`; rows under the project in the rail beside #504's Browser tab rows; a
     `ports_list` MCP tool so agents stop guessing ports.
   - *Size.* M.
   - *Hard.* Walking every process's fd table has a cost: scan while the rail is visible (Orca: every
     30 s) or when a row expands. Containers and SSH hosts need their own scans.
   - *Sprint.* Extends #503 and #504; #510's "its own ports" becomes visible.

6. **Worktree agents' ergonomics** (#510, #511 queued).
   - Per-worktree shell history: `HISTFILE` per worktree through Marley's existing shell injection,
     only when the user has not set one, and a `fish_history` session name for fish, so the up
     arrow in a worktree's terminal recalls that worktree's commands. S.
   - Repo-declared first tabs and setup: Orca's `defaultTabs` (title, colour, command) created once
     per new worktree, the setup script in a tab or a split, and nothing a repo supplies runs until
     the user approves that script's hash. S to M.
   - Fork an agent into a new worktree: the last 800 rows, escapes stripped, capped at 36,000
     characters keeping the newest, as the first prompt of an agent on a new branch. S to M.
   - Per-worktree hostnames for dev servers, only if #507's per-project browser contexts do not
     already separate them: browsers key cookies by host, not by port, so `localhost:3000` and
     `localhost:3001` share a login. M.
   - Keep Marley's own files out of commits: Orca's `.orca/drops/` shows the failure (`git add -A`
     picks it up); put any path Marley writes inside a worktree into `.git/info/exclude`. S.

7. **Agent-aware copy and paste.** Each S, in `marley_terminal` plus small touchpoints.
   - Copy without the agent's gutter: drop the leading spaces every non-blank line shares (60 lines in
     Orca, `src/shared/terminal-selection-gutter.ts`).
   - Bracket multi-line pastes, and rich input's sends, whenever an agent runs in the terminal,
     whether or not DECSET 2004 was seen.
   - Paste a dropped image's path raw inside a bracketed paste, which Claude Code's attachment check
     expects; `add_paths_to_terminal` shell-quotes it.

8. **An agent board in its own window.**
   - *Why.* Orca's pop-out board (Needs You, Working, Done) with a live terminal dialog you can type
     into lets you answer prompts from a second monitor without switching projects.
   - *Lands in.* A gpui window drawing `marley_fleet`'s snapshot; the dialog a display-only Zed
     terminal fed from the same terminal, input routed back.
   - *Size.* L.
   - *Hard.* Two views of one PTY, which has one size: Orca's dialog claims it and parks the main
     window's pane until the dialog closes.
   - *Sprint.* After #508.

9. **One palette over agents, projects and verbs.**
   - *Why.* Orca's Cmd-J finds a worktree by branch, PR number or port, lists recent agents with their
     state, runs verbs (new terminal, new browser tab, create worktree), and offers "create" when
     nothing matches. Marley splits this between the command palette, the file finder and the rail
     switcher.
   - *Lands in.* A Marley modal over `marley_rail`'s rows and Zed actions. M.

10. **Teaching Marley's own features**, only if Marley gets users besides Chad: a first-used and
    count table per feature, and in-place popovers that advance when the user does the thing. M.

11. **Small ones.** Tab colours; saved agent prompts per project (Zed tasks cover saved commands);
    the prompt-cache countdown on agent rows. S each.

## 4. Skip

- The Node daemon as built: 60,000 lines, 36 wire versions, three VT parsers per byte, a 15-level
  class chain. Take its rules; keep live processes in the harness.
- xterm.js and the renderer's parking machinery: gpui draws alacritty grids without a JavaScript heap
  per pane.
- Monaco, its autosave (off by default, blind writes) and the TipTap editor: Zed's editor is stronger.
- The plugin system: unsandboxed Node workers, a 13-method API, three of eight listed plugins
  installable. Zed's WebAssembly extensions are the better base.
- The settings store, keybinding file, theme system and icon table: Zed is ahead on each.
- Machine-translated UI languages: Marley's one user reads English.
- Dictation inside the app (sherpa-onnx in Electron's main process): Voxtype runs outside Marley.
- Permission-bypass flags as the default agent arguments.
- The star nag, telemetry on by default, and the feature wall's hand-coded animations.
- The floating workspace: Hyprland's scratchpads do it outside the app.
- Inline images for now: alacritty has no graphics support, and agents do not print images.
- Eight usage meters in the status bar, and keep-awake: the dev box never suspends on idle.
- The localhost label proxy, if per-project browser contexts (#507) separate cookies anyway.
